# Model card - success model (`success_model.json`)

**What it does.** For every agent run it estimates the probability that the run *really* succeeded
(the backend did the work, no policy was broken, and the reply told the truth). It reads only the
log: tool failures, retries, what the agent claimed, and the policy findings of the analyzer. It
never sees the ground-truth outcome when it predicts.

**Model.** L2-regularised logistic regression on analyzer features, Platt-calibrated on out-of-fold
scores, saved as plain JSON. Prediction is pure Python (`arc/model.py: predict`): no numpy or
scikit-learn needed at runtime. Each prediction lists its strongest factors in plain English.

**Sign constraints.** Failure signals (errors, time-outs, unrecovered failures, retries, claims of
actions that never happened, critical/high/medium findings) may only *lower* the probability, and
giving a final answer may only raise it (`model.EXPECTED_SIGNS`). A feature that would get the
wrong sign is dropped (coefficient 0) and the model is refitted, so explanations never read
backwards. Dropped in the shipped model: `n_refused`, `fail_rate`, `n_retries` (their information
is already carried by `n_errors`, `n_unrecovered_failures` and the findings).

## Data - all of it ours, all of it synthetic

| Dataset | Runs | Role |
|---|---|---|
| **ShopDesk** - online-store support agent, `build/samples/training/shopdesk_train_arl.jsonl` (generated on demand), policy `sample_logs/shopdesk_policy.yaml` | 600 (2 versions x 300; 275 distinct orders) | **Training and model selection** |
| **SkyDesk** - airline customer-service agent, `build/samples/skydesk_arl.jsonl` (generated on demand), policy `sample_logs/skydesk_policy.yaml` | 300 (2 versions x 150) | **Test only** - never used for fitting or for choosing anything |

Both are generated by `scripts/generate_sample_logs.py` (stdlib only, deterministic:
ShopDesk seed 11, SkyDesk seed 7) into the git-ignored `build/samples/` by `make samples` or
automatically by `make train`. No real customers, orders, bookings or cards.

The two agents differ in domain (retail vs airline), tools (10 each; only `verify_customer`,
`issue_refund` and `escalate_to_human` share a name), policy, task mix, models (ShopDesk: gpt-4o-mini / gemini-2.5-flash;
SkyDesk: gpt-4.1-mini / gpt-5-mini) and failure-mode rates. Ground truth in both comes from a
simulated backend plus an audit of the reply, not from the planted failure label, and includes
noise the log cannot show (refunds reversed at settlement, labels voided, e-mails bouncing).

Base rates: ShopDesk 54.3% (v1 47.0%, v2 61.7%); SkyDesk 56.3% (v1 47.3%, v2 65.3%).

## Protocol (fixed before any SkyDesk number was seen)

1. Ten candidates were listed in advance: feature set `full` (24 features) or `generic`
   (17 domain-neutral features) x L2 in {0.3, 1, 3, 10, 30}.
2. Each was scored with **order-grouped 5-fold cross-validation on ShopDesk only** (every contact
   about one order stays in one fold).
3. The winner was picked by ShopDesk CV AUC (3 d.p.), ties to the lower Brier score.
4. The chosen model was then scored **once** on SkyDesk (v1, v2, all). The fallback heuristic was
   scored on the same runs.

Reproduce: `make train` (or `python scripts/train_success_model.py`; it generates both data sets
first if they are missing). All numbers below are in `training_report.json`.

because Platt scaling is fitted on the same out-of-fold scores; AUC is not affected.

### SkyDesk, never seen (test, evaluated once)

| Runs | n | Model AUC | Model Brier | Model acc. @0.5 | Heuristic AUC | Heuristic Brier |
|---|---|---|---|---|---|---|
| skydesk-v1 | 150 | 0.987 | 0.009 | 0.993 | 0.985 | 0.104 |

On all 300 SkyDesk runs the model makes 2 mistakes at the 0.5 threshold (2 failures predicted as
successes, 0 successes predicted as failures). Mean predicted success 0.556 against an actual
0.563. The heuristic ranks almost as well on v1, but it is much less calibrated (it starts every
clean run at 85%).

## Limitations - read before trusting the numbers

* **The data is synthetic, and both agents come from one generator.** ShopDesk and SkyDesk share the
  same family of planted failure modes, the same log conventions and the same style of backend audit.
  That makes the SkyDesk test much easier than a real new agent would be. The near-perfect scores
  above show that the model learned *this generator's* failure signals well; they are **not** an
  estimate of accuracy on real agents. **Expect real-world accuracy to be clearly lower**, and expect
  the model to be over-confident there: on these logs it often outputs 1% or 98%.
* **It cannot see what the log does not show.** A refund reversed later, a label voided by the carrier,
  or an e-mail that bounced all look like clean runs. Those, plus a timed-out call that did go through
  and was then repeated, and a few claims in the reply that the text parser misses, are the errors it
  still makes on these logs.
* **Wrong decisions that look healthy are invisible.** If an agent does the wrong thing confidently
  and every tool call succeeds, there are no failure signals to score.
* **The chosen `full` feature set includes raw counts** (steps, tools, distinct tools). They helped on
  ShopDesk and did not hurt on SkyDesk, but on an agent with much longer or shorter runs they can shift
  probabilities for reasons unrelated to success. If you analyse a very different agent, retrain with
  `--features generic` (CV AUC 0.981 on ShopDesk) or, better, on your own labelled runs.
* **Policy matters.** `n_critical` is the strongest feature, and critical findings come from the policy
  you upload. A policy that does not describe your agent produces wrong findings and wrong probabilities.
  How to write one: `docs/POLICY_FORMAT.md` (in the app: Step 2 -> "What should a policy look like?").
* **Calibration was fitted on a 54% base rate.** On agents that succeed far more or far less often,
  the ranking (AUC) holds up better than the absolute probabilities.
* Cost and latency are not features.

## Retrain on your own agent

Any log format the app accepts works, as long as runs carry `outcome.verified_success`:

```bash
.venv/bin/python -m arc.model train my_runs.jsonl --policy my_policy.yaml --features generic \
    --out arc/models/success_model.json --source "my agent, 2026-10, 800 labelled runs"
```

Use a grouping key (`meta.case_id`) when the same task appears several times, so cross-validation
does not leak between repeats.
